1시스템 개요와 권한

이 시스템은 쇼핑 고객의 질의를 입력 → 실행(Tool) → 출력 3단계 가드레일로 검사하는 FastAPI 게이트웨이와, 그 결과를 모니터링하는 Streamlit 보안 관제 콘솔로 구성됩니다. AI 모델(로컬 Ollama qwen3:8b)은 권한 판정자가 아니며, 상품·주문 조회와 고객이 확인한 장바구니·쿠폰 변경만 허용됩니다.

  • 대시보드·감사 상세·세션 보고서 조회
  • 규칙·정책 조회 및 검증 결과 확인
  • 합성 검증 챗 사용
  • 규칙 편집·게시는 불가

  • operator의 모든 권한
  • 규칙 draft 수정·검증·게시·롤백
  • 규칙 게시 시 재인증(비밀번호) 필요
  • 계정 발급(내부 CLI)
⚠️ 채널 분리고객(customer) 계정은 관제(ops) 채널에서 로그인할 수 없고, operator/admin 계정은 쇼핑(shop) 채널에서 로그인할 수 없습니다. 화면 제어와 별개로 모든 API가 역할·소유권을 다시 검증합니다.

2관제 콘솔 접속·로그인

  1. 브라우저에서 https://ops.example.internal (LAB은 :8443)로 접속합니다.
  2. 발급받은 operator/admin 이메일·비밀번호로 로그인합니다. (회원가입 탭 없음)
  3. 로그인 성공 시 최근 24시간(Asia/Seoul) 기준 대시보드가 열립니다.
💡 접속 전 준비관제 PC에 사내 CA(ca.crt) 설치와 hosts 등록(10.10.70.149 shop.example.internal ops.example.internal)이 되어 있어야 합니다. 상세는 9장 참고.

3관제 대시보드

로그인 직후의 기본 화면입니다. 기간·세션·상태 필터를 바꾼 뒤 [조회]를 눌러 적용합니다. 활성 대시보드의 통계는 10초마다 자동 갱신됩니다.

4감사 이벤트 상세

대시보드 목록에서 event_id를 누르면 해당 이벤트의 상세를 봅니다.

┌─────────────────────────────────────────────────────────┐ │ 감사 상세 [목록으로] │ │ event_id / request_id / session_id / 발생시각 / source │ │ status / stage / ruleset_version / model │ │ input_ms / output_ms / total_ms │ │ 마스킹 요약 │ │ 룰 ID | 설명 | OWASP 2025 | 단계 | action | match_count │ │ Tool | outcome | target_id | action_id | duration_ms │ │ (LAB만) 차단된 입력 원문 — 일반 텍스트 │ └─────────────────────────────────────────────────────────┘
  • 적중한 룰 ID·설명·OWASP 분류·단계(입력/실행/출력)와 처리 시간을 확인합니다.
  • rule_id·ruleset_version은 규칙 관리 화면의 해당 불변 버전으로 연결됩니다.
🔒 운영 환경 비공개 원칙운영에서는 raw 입력·raw 응답·토큰·비밀 매칭값을 표시하지 않습니다. 차단된 입력 원문은 LAB(합성 데이터) 환경에서만 일반 텍스트로 열람 가능합니다. actor_id는 이메일 대신 내부 식별자로 표시되며, 관리자가 고객 승인을 대신하는 버튼은 없습니다.

5규칙·정책 관리 (게시·롤백)

admin 전용 변경   operator는 조회·검증 결과 확인만 가능합니다.

┌─────────────────────────────────────────────────────────┐ │ 버전 목록: label | state | checksum | 게시시각 │ │ [복제하여 draft 만들기] │ │ 룰: ID / stage / category / kind / pattern / flags │ │ action / marker / priority │ │ 정책: 길이·출력·도구 예산, 운영 강제값 │ │ [draft 저장] [검증] 결과: case 수·실패 code │ │ [게시] / [이 버전으로 롤백] → 재인증·확인 dialog │ └─────────────────────────────────────────────────────────┘

규칙 버전 상태(생명주기)

상태가능한 동작
draftadmin이 수정·저장, 검증 실행
validated내용 수정 불가, 재인증 후 게시 가능
active현재 운영 중. 읽기 전용 → 복제(clone)로만 수정
retired읽기 전용. 검증·재인증 후 롤백 대상

새 규칙 게시 절차

  1. 현재 active 버전에서 [복제하여 draft 만들기]를 누릅니다.
  2. 룰(패턴·단계·action·priority)과 정책(길이·출력·도구 예산)을 수정하고 [draft 저장].
  3. [검증]을 실행합니다. 시험 case 통과 수와 실패 code가 표시됩니다. 검증을 통과하지 못하면 게시 버튼이 비활성입니다.
  4. [게시]를 누르면 확인 dialog가 뜹니다. 후보 label·checksum·현재 active ID·영향 규칙 개수와 재인증 비밀번호를 확인·입력합니다.
  5. 게시가 완료되면 새 버전이 active가 됩니다.
⚠️ 롤백문제가 생기면 retired 버전을 선택해 검증 → 재인증 → [이 버전으로 롤백] 순으로 되돌립니다. 충돌·검증 실패 시 기존 버전이 유지되고 실패 code가 표시됩니다. 재인증 비밀번호는 제출 후 메모리에서 제거되며 저장되지 않습니다.
💡 CLI로 최초 룰셋 부트스트랩최초 1회는 명령으로 기본 룰셋을 심습니다: docker compose exec api python -m app.cli.rules bootstrap --actor-email admin@example.internal

6세션 보고서·PDF

┌─────────────────────────────────────────────────────────┐ │ 세션 보고서 │ │ 기간 [시작][종료] 세션 UUID [ ] [미리보기] │ │ 건수 / status / OWASP / 지연 / 룰 버전 / 적재 시각 │ │ [PDF 다운로드] │ └─────────────────────────────────────────────────────────┘
  1. 기간(최대 31일)과 필요 시 세션 UUID를 입력하고 [미리보기]로 통계를 확인합니다.
  2. [PDF 다운로드]로 보고서를 받습니다. 파일명은 security-report-YYYYMMDD.pdf입니다.
  • PDF에는 제목·기간·시간대·as_of·적재 지연·집계 단위·룰 버전·생성자 내부 ID·마스킹 이벤트 요약이 포함됩니다.
  • 최대 이벤트 10,000건으로 제한됩니다. 생성 중 중복 클릭은 잠기며, 오류 시 빈 PDF가 내려받아지지 않습니다.
  • PDF 바이트는 관제 서버가 내부망에서 받아 제공하며, 브라우저가 관리 API에 직접 접근하지 않습니다.
⚠️ 수치 표기합성 시험 방어율과 실제 이벤트 차단 비율을 같은 값으로 표시하지 않습니다. 보고서에서도 둘을 구분해 해석하세요.

7합성 검증 챗

운영 룰셋이 실제로 어떻게 동작하는지 합성(가짜) 데이터로 안전하게 시험하는 화면입니다.

┌─────────────────────────────────────────────────────────┐ │ 합성 검증 챗 — 운영 🛡️ 보안 보호 활성 │ │ [새 검증 세션] 합성 데이터 안내 │ │ 질의 [ ] [검증] │ │ 정제 응답 / status / stage / rule_ids / ruleset_version │ │ input_ms / output_ms / total_ms [감사 이벤트 찾기] │ └─────────────────────────────────────────────────────────┘
  • 질의를 보내면 실제 운영 룰셋으로 검사한 결과와 적중한 rule_ids를 보여줍니다.
  • 실제 고객 주문·개인정보·키를 입력하지 마세요. 합성 데이터만 사용합니다.
  • [감사 이벤트 찾기]로 방금 검증의 감사 기록을 request_id로 조회할 수 있습니다(적재 전엔 “적재 대기” 표시).

8LAB ON/OFF A/B 비교 LAB 전용

가드레일을 껐을 때(OFF)와 켰을 때(ON)의 차이를 시험셋으로 자동 비교하는 화면입니다. APP_ENV=lab에서만 메뉴·API가 존재하며 운영(production)에는 없습니다.

┌─────────────────────────────────────────────────────────┐ │ LAB 환경 — 합성 데이터 전용 (운영 아님) │ │ 시험셋 [공격 v1 ▼] 범주 [전체 ▼] [A/B 실행] 진행 12/200 │ │ 요약: OFF 유출 n → ON 차단 n·마스킹 n·미방어 n │ │ case | 범주 | OFF 결과 | ON 결과 | 막은 계층 | rule_ids │ │ [사례 상세: OFF vs ON 비교] [리포트 PDF] │ └─────────────────────────────────────────────────────────┘
  1. 시험셋과 범주를 고르고 [A/B 실행]을 누릅니다. 진행률이 표시됩니다.
  2. 요약에서 OFF 유출 → ON 차단·마스킹·미방어 건수를 확인합니다.
  3. 각 case의 막은 계층(가드레일 입력/실행/출력 · 권한 통제 · 미방어)과 rule_ids를 비교합니다.
  4. [리포트 PDF]로 모델 digest·룰셋 버전·시험셋 hash·실행 시각이 포함된 결과를 내보냅니다.
🔒 LAB 격리LAB은 운영과 완전히 분리된 환경·DB입니다(8443 포트, 합성 데이터·미끼 비밀만). 운영 데이터는 보이지 않으며, LAB 탐지율은 운영 탐지율과 구분해 표기합니다. 데모·시연은 반드시 LAB 기준으로 하세요.

9운영·배포 (Docker)

모든 서비스는 Docker Compose로 뜹니다. 필요: Docker Desktop, Python 3.12. 아래는 LAB(8443) 기준이며, 운영은 --env-file .env.lab을 빼고 실행합니다.

최초 기동

# 1) 환경파일·키·인증서 생성
python scripts/gen_env.py                 # .env (임의 비밀번호, 커밋 금지)
python scripts/gen_jwt_key.py             # secrets/jwt_private.pem
python scripts/gen_certs.py               # secrets/tls/ 사설 CA·서버 인증서

# 2) DB 기동·스키마 적용
docker compose up -d --wait postgres
docker compose run --rm migrate

# 3) 전체 서비스 기동
docker compose up -d --wait api audit-worker scheduler streamlit nginx

# 4) LAB 환경(운영과 분리, 8443)
LAB_ADMIN_PASSWORD='12자 이상 비밀번호' sh scripts/lab_up.sh

코드 수정 후 반영(재실행)

lab_up.sh는 최초 1회만 실행합니다. 이후에는 고친 부분만 다시 띄웁니다.

고친 곳반영 방법 (LAB 기준)
쇼핑몰 frontend/shop/저장만 하면 됨(nginx 직접 연결). 브라우저 Ctrl+F5
관제 frontend/ops/docker compose --env-file .env.lab up -d --build --wait streamlit
서버 backend/app/docker compose --env-file .env.lab up -d --build --wait api audit-worker scheduler
DB 마이그레이션... build migrate && ... run --rm migrate
nginx·인증서docker compose --env-file .env.lab restart nginx
전부 한 번에docker compose --env-file .env.lab up -d --build --wait
  • 상태 확인: docker compose --env-file .env.lab ps → 모두 Up (healthy)이어야 합니다.
  • PC·Docker 재시작 시 컨테이너는 자동으로 다시 뜹니다(restart: unless-stopped). 안 떴으면 “전부 한 번에”를 실행.
  • 종료: docker compose --env-file .env.lab down (데이터 유지). 데이터까지 삭제: down -v.

다른 PC에서 접속·시연 준비

  1. hosts(C:\Windows\System32\drivers\etc\hosts)에 10.10.70.149 shop.example.internal ops.example.internal 추가
  2. ca.crt 한 파일만 복사(ca.key·server.key는 복사 금지) 후 관리자 PowerShell:
    Import-Certificate -FilePath <경로>\ca.crt -CertStoreLocation Cert:\LocalMachine\Root → 브라우저 재시작
  3. 시연은 LAB 기준: 쇼핑 https://shop.example.internal:8443, 관제 https://ops.example.internal:8443
🔒 비밀 파일 취급개인키(jwt_private.pem, ca.key, server.key)와 .env·비밀번호 파일은 절대 커밋·공유하지 않습니다. 배포 대상 PC에는 ca.crt만 전달합니다.

10계정 관리

관리 계정(operator/admin)은 공개 API가 아닌 내부 CLI로만 생성합니다. 비밀번호는 명령 실행 중 프롬프트로 입력하며, 명령줄·로그에 남기지 않습니다.

# 관리자 계정 생성 (비밀번호는 프롬프트 입력)
docker compose exec api python -m app.cli.create_user \
  --email admin@example.internal --role admin

# 고객 합성 데이터 시드(데모용)
docker compose run --rm migrate python -m app.cli.seed \
  --customer-email <가입한 고객 이메일>
계정 종류발급 방법
고객(customer)쇼핑 웹 회원가입
operator / admin위 CLI(create_user)로만 발급
⚠️ 비밀번호 보관LAB/운영 관리자 비밀번호는 secrets/ 아래 커밋 제외 파일에 보관됩니다(예: secrets/prod_admin_password.txt, secrets/lab/e2e_admin_password.txt). 외부 유출·화면 공유에 주의하세요.
