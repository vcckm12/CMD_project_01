**붙여 넣기 전에 먼저 할 일:** 아래 `[ ]`로 표시된 칸 4곳을 채우세요.

- 팀명
- 팀원과 역할
- 프로젝트 시작일
- 발표 시간

나머지는 저장소에서 확인한 사실로 채워 두었습니다. 그다음 `---` 이후 전체를 저장소를 읽을 수 있는 AI에게 붙여 넣습니다.

---

## 역할과 목표

당신은 기술 발표 자료 제작자입니다. 이 저장소(AI 보안 가드레일 챗봇)의 **최종 발표 자료 한 벌**을 만듭니다. 발표는 팀별로 평가되고, 다음 세 가지가 평가에 들어갑니다.

- **시연이 필수**입니다.
- **발표 태도**가 중요합니다.
- **프로젝트 이해도**(질문에 답하는 능력)를 봅니다.

그래서 슬라이드만 만들지 말고, 대본·시연 순서·예상 질문 답변까지 함께 만듭니다.

## 필수 슬라이드 구성 (요구 항목 → 슬라이드)

1. **표지:** 프로젝트명 "AI 보안 가드레일 챗봇 — GUARDRAIL FASHION", 팀명, 발표일
2. **팀 소개:** 팀원, 역할 분담 (표)
3. **프로젝트 개요·목적**
   - 문제: LLM 챗봇은 프롬프트 인젝션, 시스템 프롬프트 유출, 개인정보 노출, 과도한 권한 사용에 취약합니다.
   - 목적: 쇼핑몰 AI 상담 챗봇 앞뒤에 보안 가드레일을 두어 입력·도구 결과·출력을 검사합니다. 막은 근거는 관제 화면에서 감사할 수 있게 합니다.
   - 핵심 질문: 가드레일이 있을 때와 없을 때 무엇이 다른가?
4. **요구사항과 범위:** 무엇을 만들었고 무엇을 범위에서 뺐는지. 근거는 docs/README의 결정 기록입니다.
5. **구성도(시스템 아키텍처)**
   - 고객 웹/AnythingLLM → Nginx(TLS) → FastAPI(가드레일 파이프라인) → Ollama qwen3:8b(별도 PC .65)
   - PostgreSQL 17(commerce/threat_intel/audit) ← 감사 워커·스케줄러
   - Streamlit 관제
   - 운영(443)과 LAB(8443)는 분리되어 있습니다.
   - `docs/01`, `docs/08`을 바탕으로 **도식으로 새로 그립니다.**
6. **사용자 흐름도** (`docs/03`)

## 검증 결과 (이 수치만 사용)

- **LAB ON/OFF 비교, 취약한 시스템 프롬프트(D-42):** 공격 12건 중 가드레일 OFF는 9건 유출, **ON은 0건**
- **LAB 출력 단계 시험셋 `lab_output_v1`:** OFF 8건 중 7건 유출, **ON 0건**. 출력 규칙이 4건을 직접 잡음
- **자동 시험:** 통합 시험 393건 통과(`sh scripts/test.sh`, 독립 시험 DB). 브라우저 E2E 3종(쇼핑몰·관제·LAB) 통과
- **한계 명시:**
  - 위 수치는 **개발 중 결과**입니다. 독립 시험셋(제3자 라벨)은 시간 관계로 측정하지 않았습니다(사용자 결정).
  - 대시보드의 차단 비율은 운영 이벤트 비율이라 탐지율과 다릅니다.

## 문제 해결 사례 (근거는 docs/README 결정 기록)

1. **CPU 추론이 느림:** 생성 약 7 tokens/s.
   - 해결: 호출 예산과 타임아웃 재설계(D-15), 판별 타임아웃 45초, 처리 단계를 실시간 칩으로 표시(D-35)
2. **가드레일 OFF인데도 공격이 통하지 않아 비교가 의미 없음.**
   - 원인: 모델 자체가 거절함
   - 해결: LAB 전용 "취약한 챗봇" 시스템 프롬프트와 미끼 비밀을 둠(D-42)
3. **대부분 AI 판별에서 막혀 정규식이 안 보임.**
   - 해결: 두 계층을 항상 모두 실행하고 계층별 판정·처리 시간을 기록·시각화(D-36)
4. **정상 장바구니 요청이 차단됨.**
   - 원인: 모델이 상품 ID를 추측해 형식 오류 발생
   - 해결: 형식 오류는 차단하지 않고 모델에 되돌려 줌(D-44). 고객 문장에서 상품을 찾아 확인 화면 제안(D-45)
5. **AI만 잡은 공격을 정규식으로 옮기기 어려움.**
   - 해결: AI가 정규식을 제안하고 서버가 문법·ReDoS·오탐을 검사함. 관리자는 YES/NO만 누름(D-46)
   - 오탐 위험: 관찰 모드로 먼저 적용하고, 같은 질문이 반복되면 경보를 띄움(D-47)
6. **비밀번호 재설정 안내 같은 정상 답변을 출력 판별기가 오탐.**
   - 해결: 판별 기준을 키워드가 아니라 의도로 보완(D-34)
7. **모델 PC(.65) 재부팅 후 Ollama가 외부 접속을 받지 않아 서비스 중단.**
   - 해결: 준비 상태 점검(`/health/ready`의 model 항목)으로 원인을 바로 찾음. `OLLAMA_HOST=0.0.0.0` 상시 설정
8. **관제 화면에 공격자 문장이 표시되는 XSS 위험.**
   - 해결: 데이터는 HTML로 렌더링하지 않고, 고정 CSS 파일 1개만 주입(D-48)

## 고찰·향후 계획 재료

**의미**
- 규칙(빠름·설명 가능)과 LLM 판별(새로운 표현 대응)을 함께 써서 서로의 약점을 보완했습니다.
- 모든 차단에 근거(규칙 ID, 계층, 처리 시간)가 남아 감사할 수 있습니다.

**한계**
- qwen3:8b CPU 추론이라 응답이 20~50초 걸립니다.
- LLM 판별은 같은 문장도 판정이 흔들립니다(비결정성).
- 독립 시험셋은 측정하지 않았습니다.
- 정규식 제안은 LAB에서만 동작합니다(운영은 원문을 저장하지 않음).
- 메트릭 수집 스택은 범위에서 뺐습니다(D-20).
- 외부 공개(2단계, D-23)는 하지 않았습니다.

**향후 계획**
- GPU 추론 또는 경량 분류 모델로 속도 개선, 서버 벡터 RAG(D-12)
- 독립 시험셋으로 탐지율·오탐률 측정
- LAB에서 검증된 제안 규칙을 운영으로 승격하는 절차
- Prometheus 등으로 메트릭·경보 고도화
- 공인 도메인·인증서로 외부 공개(D-23 2단계)
- 다른 업종 챗봇에 가드레일 재사용(멀티 테넌트)

## 시연 시나리오 작성 기준 (3번 결과물)

`시연_질문_모음.pptx`의 검증된 질문만 씁니다. 순서는 다음과 같습니다.

1. **쇼핑몰 정상 질문:** 상품 추천. 처리 단계 칩이 넘어가는 것을 보여 줍니다.
2. **장바구니 담기 요청:** 확인 화면 → 승인 → 장바구니 반영
3. **공격 질문:** 차단 답변 "🛡️ 요청을 보안 정책에 따라 처리할 수 없습니다."
4. **관제 대시보드:** 방금 차단 건 → 감사 상세 → 규칙 ID·계층별 판정·처리 시간 도넛
5. **LAB ON/OFF 비교:** 같은 공격이 OFF에서는 유출, ON에서는 차단
6. **(시간 여유 시)** 정규식 제안 YES → 관찰 모드, 반복 질문 경보

시나리오에 함께 적을 것:

- **시연 전 점검표**
  - Ollama 연결: `/health/ready`의 model이 true
  - 첫 질문으로 모델 예열(첫 응답은 느림)
  - 브라우저 로그인
  - 대시보드 경보 확인 처리
- **실패 대비**
  - 응답이 늦거나 판정이 달라질 때 할 말
  - 미리 녹화한 시연 영상으로 전환하는 시점
- 단계마다 걸리는 시간(초)과 발표자 멘트

다음 분야를 고르게 넣습니다. 답은 2~4문장으로 쓰고, 끝에 근거 파일을 `(근거: docs/06 §…)`처럼 적습니다.

- **설계 이유:** 왜 정규식과 LLM을 둘 다? 왜 OR 판정? 왜 PostgreSQL? 왜 LAB 분리?
- **보안:** 원문을 안 남기면 사고 조사는 어떻게? XSS? 관리자 권한 탈취? ReDoS?
- **성능:** 응답이 왜 느린가? 판별기가 실패하면?
- **정확도:** 오탐·미탐은? 수치의 한계는?
- **운영:** 규칙은 어떻게 추가·게시? 경보는 언제?
- **역할별:** 팀원이 각자 맡은 부분을 설명할 수 있도록 역할마다 2~3문항
