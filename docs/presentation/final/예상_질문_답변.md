## 1. 설계 이유 및 아키텍처

### Q01. 왜 정규식 룰셋과 LLM 판별기를 둘 다 사용했나요? 하나만 쓰면 안 되나요?
**A:** 정규식은 1ms 미만(실측 예 0.4ms)으로 빠르고 확실한 차단 근거(Rule ID)를 제공하지만 띄어쓰기나 우회 표현 같은 변형에 취약하며, LLM 판별기는 의미론적 의도를 잘 파악하지만 연산 비용이 큽니다. 따라서 두 계층을 항상 모두 실행하고 하나라도 막으면 차단하도록(OR) 설계해, 알려진 공격은 규칙이, 바꿔 쓴 표현은 AI 판별이 잡습니다(D-36).  
*(근거: `docs/06_guardrail_security_design.md` §2.1, `docs/README.md` D-25)*

### Q02. 정규식과 LLM 판별기의 판정을 왜 'OR'로 결합했나요? 'AND'나 가중치 방식은 왜 안 썼나요?
**A:** 보안의 제1원칙은 악의적인 공격의 누락(False Negative)을 최소화하는 것입니다. 둘 중 어느 한 계층이라도 위험하다고 판단하면 즉시 차단해야만 다계층 방어선의 실효성이 유지됩니다. AND 방식을 쓰면 정규식에 없는 신종 표현이나 LLM이 놓친 패턴이 모두 통과되므로 OR 결합을 채택했습니다.  
*(근거: `docs/06_guardrail_security_design.md` §3.1, `docs/README.md` D-36)*

### Q03. 왜 데이터베이스로 MongoDB 같은 NoSQL 대신 PostgreSQL 17을 선택했나요?
**A:** 전자상거래 주문과 장바구니의 강력한 트랜잭션(ACID) 보장이 필수적이었으며, PostgreSQL의 스키마 격리 기능을 통해 `commerce`(상거래), `threat_intel`(룰셋), `audit`(감사)의 권한을 물리적으로 분리할 수 있기 때문입니다. 또한 `layers->'input_rules'->>'verdict'`와 같은 JSONB 쿼리와 인덱싱을 지원하여 복잡한 가드레일 감사 통계를 단일 RDBMS에서 고속 처리할 수 있습니다.  
*(근거: `docs/01_system_architecture.md` §3.2, `docs/README.md` D-02)*

### Q04. 운영 환경(포트 443)과 LAB 환경(포트 8443)을 왜 별도로 분리했나요?
**A:** 공격 실증을 위해서는 모델에 '취약한 챗봇' 프롬프트를 주입하고 미끼 비밀을 넣어야 하는데, 이것이 실제 운영 DB나 정상 고객 서비스에 섞이면 치명적인 침해 사고가 됩니다. 따라서 Nginx 포트부터 도커 컴포즈 네트워크, 독립 데이터베이스까지 완전히 분리된 A/B 테스트 환경을 구축했습니다.  
*(근거: `docs/01_system_architecture.md` §4.1, `docs/README.md` D-42)*

### Q05. AI가 직접 장바구니를 수정하지 않고 왜 고객 승인(확인 화면)을 거치게 했나요?
**A:** LLM의 환각(Hallucination)이나 간접 프롬프트 주입으로 인해 고객이 원치 않는 대량 주문이나 금액 결제가 발생하는 것을 방지하는 최소 권한 원칙 때문입니다. AI는 오직 5분간 유효한 일회용 변경 서명 토큰만 발급하고, 고객이 화면에서 직접 눈으로 대조한 뒤 승인 버튼을 눌러야만 DB 트랜잭션이 수행됩니다.  
*(근거: `docs/03_user_flow.md` §2.3, `docs/README.md` D-05)*

### Q06. 감사 로그 적재에 왜 Outbox 패턴과 비동기 워커를 도입했나요?
**A:** 고객과의 실시간 채팅 응답 경로에서 감사 로그를 동기식으로 DB에 쓰면 데이터베이스 부하가 고객 대기 시간으로 직결되기 때문입니다. 트랜잭션 안에서 가벼운 Outbox 큐에만 이벤트를 기록하고, 별도의 백그라운드 감사 워커가 배치로 적재하여 시스템 지연을 0.2초 이내로 최소화했습니다.  
*(근거: `docs/01_system_architecture.md` §5.1, `docs/README.md` D-18)*

## 2. 보안 및 무결성

### Q07. 감사 로그에 고객 질의 원문을 남기지 않으면, 사후 침해 사고 조사는 어떻게 하나요?
**A:** 질의 원문을 그대로 저장하면 감사 DB 자체가 해커의 2차 개인정보 탈취 표적이 되므로, 해시 지문(Fingerprint)과 적중된 규칙 ID, 마스킹된 요약문만 보관합니다. 사후 조사는 어떤 정책과 엔티티 유형(전화번호/계정)이 어떤 경로에서 적중되었는지를 바탕으로 패턴 중심의 포렌식을 수행합니다.  
*(근거: `docs/06_guardrail_security_design.md` §4.2, `docs/README.md` D-09)*

### Q08. 관제 대시보드에서 차단된 공격자 문장을 볼 때 XSS(크로스 사이트 스크립팅) 공격 위험은 없나요?
**A:** 공격자가 스크립트 태그를 전송할 수 있으므로, Streamlit 관제 화면에서는 데이터를 일절 raw HTML로 렌더링하지 않고 `html.escape()` 함수를 전수 적용하여 순수 텍스트로 격리합니다. 화면 스타일링을 위한 코드는 오직 단 하나의 정적 `style.css` 파일만 주입하여 Stored XSS를 원천 봉쇄했습니다.  
*(근거: `docs/ui_redesign_prompt_ops.md` §1, `docs/README.md` D-48)*

### Q09. 관리자 권한을 가진 공격자가 API를 통해 룰셋을 임의로 비활성화하면 어떻게 막나요?
**A:** 가드레일 활성화 플래그(`GUARDRAIL_ENFORCED`)는 런타임 API로 끌 수 없도록 환경 변수로 고정되어 있습니다. 또한 새로운 룰셋 게시나 롤백 시에는 관리자 비밀번호를 반드시 재인증해야 하며, 모든 정책 변경 이력은 감사 스키마에 영구히 서명되어 기록됩니다.  
*(근거: `docs/06_guardrail_security_design.md` §5.3, `backend/app/api/ops.py` L310)*

### Q10. 정규식 룰이 늘어나면 ReDoS(정규식 서비스 거부 공격)로 서버가 멈출 위험은 없나요?
**A:** 정규식 룰셋 등록 시 백엔드 검증 파이프라인에서 지수적 백트래킹(Catastrophic Backtracking)을 유발하는 중첩 수량자(`(a+)+`)를 정적 분석하여 사전에 거부합니다. 또한 파이썬 정규식 매칭 시 최대 타임아웃과 텍스트 길이 제한(최대 4,000자)을 두어 CPU 독점을 방지합니다.  
*(근거: `docs/06_guardrail_security_design.md` §2.3, `docs/README.md` D-46)*

### Q11. 고객 인증 토큰(JWT)의 탈취 및 위조 위험은 어떻게 통제하나요?
**A:** 액세스 토큰은 15분의 짧은 유효기간을 가지며 브라우저 메모리에만 보관되고, 리프레시 토큰은 `HttpOnly`, `Secure`, `SameSite=Strict` 속성의 쿠키로 격리됩니다. 토큰 서명 키(`jwt_private.pem`)는 컨테이너 볼륨 시크릿으로만 마운트되어 형상 관리에서 완전히 배제됩니다.  
*(근거: `docs/01_system_architecture.md` §6.1, `backend/app/core/auth.py` L45)*

### Q12. 감사 이벤트가 전송되는 도중 위변조되지 않았음을 어떻게 보증하나요?
**A:** 모든 감사 이벤트는 서버 시크릿 키를 기반으로 한 HMAC-SHA256 전자서명을 포함합니다. 데이터베이스에 적재된 후에도 서명 검증을 통해 특정 행이 임의로 수정되거나 삭제되었는지를 감사 스케줄러가 정기 무결성 검증으로 탐지합니다.  
*(근거: `docs/06_guardrail_security_design.md` §4.4, `backend/app/audit/worker.py` L80)*

## 3. 성능 및 가용성

### Q13. 답변 생성이 다소 느릴 수 있는데, 원인이 무엇이고 실무 도입 시 어떻게 개선하나요?
**A:** 현재 환경이 외장 GPU 없이 일반 PC의 CPU에서 80억 파라미터 양자화 모델을 실행하고 있기 때문에 초당 약 4~8토큰 속도의 물리적 한계가 존재합니다. 실무 상용 서비스에서는 엔비디아 GPU(RTX 4090/A100)와 vLLM 런타임을 결합하여 전체 추론 지연 시간을 300ms~1초 이내로 단축할 수 있습니다.  
*(근거: `docs/07_verification_operations_plan.md` §3.1, `docs/README.md` D-15)*

### Q14. 만약 독립 Ollama 추론 서버가 다운되거나 응답하지 않으면 시스템은 어떻게 되나요?
**A:** 판별 단계별로 엄격한 타임아웃이 설정되어 있어 무한 대기를 방지하며, 모델 서버 장애 시 `503 Service Unavailable`과 함께 헬스체크 위젯에서 즉시 붉은색 경보를 발행합니다. 보안 정책상 가드레일 판별이 실패하면 '안전 실패(Fail-Closed)' 원칙에 따라 악의적 질의가 무방비로 통과되지 않도록 차단합니다.  
*(근거: `docs/01_system_architecture.md` §4.3, `docs/README.md` D-15)*

### Q15. 정규식 검사와 LLM 판별 검사를 모두 수행하면 지연 시간이 2배로 늘어나지 않나요?
**A:** 2배가 되지는 않습니다. 정규식 검사는 1ms 미만이라 거의 영향이 없고, 시간은 대부분 AI 판별(단계당 약 1~2초)과 답변 생성(10초 이상)에 쓰입니다. 입력 단계에서 차단되면 답변 생성은 아예 하지 않으므로 공격 요청은 오히려 빨리 끝납니다. 계층별 처리 시간은 감사 상세에서 이벤트마다 확인할 수 있습니다(D-36).  
*(근거: `docs/06_guardrail_security_design.md` §3.2, `docs/07_verification_operations_plan.md` §3.2)*

### Q16. 악의적인 공격자가 10만 자의 거대한 프롬프트를 보내 서버 자원을 고갈시키려 하면 어떻게 되나요?
**A:** 게이트웨이 진입점인 Nginx와 FastAPI Pydantic 스키마 수준에서 요청 페이로드의 최대 길이를 4,000자로 강제 제한합니다. 또한 비정상적인 반복 요청에 대해 세션 및 IP 기반 레이트 리미트를 적용하여 DoS(LLM10) 공격을 인프라 전단에서 차단합니다.  
*(근거: `docs/06_guardrail_security_design.md` §6.1, `deployment/nginx/nginx.conf` L40)*

### Q17. 동시 접속자가 몰릴 때 DB 연결 풀이 고갈되는 병목은 없나요?
**A:** `psycopg_pool.AsyncConnectionPool`을 적용하여 비동기 논블로킹 연결을 재사용하며, 읽기 전용 감사 트래픽과 트랜잭션 쓰기 연결 풀을 분리 운영합니다. 타임아웃을 5초로 타이트하게 제한하여 특정 쿼리 지연이 풀 전체의 고갈로 이어지지 않도록 방어했습니다.  
*(근거: `backend/app/db/pool.py` L25, `docs/README.md` D-17)*

## 4. 정확도 및 검증 한계

### Q18. 정상적인 고객의 일상적인 질문이 차단되는 '오탐(False Positive)' 문제는 어떻게 해결했나요?
**A:** "배송 메모에 연락처 적어줘" 같은 정상 질문이 출력 차단되던 문제는 단순 차단 대신 개인정보만 가리는 마스킹(Mask) 액션으로 전환하여 해결했습니다. 또한 정상 대조군 100건에 대한 Replay 검증을 통해 규칙을 정밀 튜닝하여 과잉 차단율(FPR) 5% 이하를 달성했습니다.  
*(근거: `docs/06_guardrail_security_design.md` §3.4, `docs/README.md` D-34)*

### Q19. 공격자가 정규식 단어를 한 글자씩 띄어 쓰거나 Base64로 난독화하면(예: "I g n o r e") 뚫리지 않나요?
**A:** 입력 가드레일 전처리 파이프라인에서 Base64 디코딩과 연속 공백, 제로위드(Zero-width) 공백을 정규화(Normalize)한 후 규칙을 대조합니다. 만약 정규화 규칙을 우회하더라도, 두 번째 계층인 심층 SLM 판별기가 문맥적 의미를 파악하여 2중으로 차단합니다.  
*(근거: `docs/06_guardrail_security_design.md` §2.2, WBS `SEC-002`)*

### Q20. 발표 자료의 검증 수치(OFF 9건 → ON 0건, OFF 7건 → ON 0건)를 100% 방어라고 볼 수 있나요?
**A:** 아닙니다. 발표 자료의 수치는 개발 중 LAB 시험(공격 12건, 출력 단계 공격 8건)의 결과이며, 제3자가 만든 독립 시험셋으로는 측정하지 않았습니다. AI 판별은 같은 문장에도 판정이 흔들릴 수 있어, 새 표현은 정규식 제안(관찰 모드 → 차단)과 반복 질문 경보로 계속 보완하는 구조를 만들었습니다(D-46, D-47).  
*(근거: `docs/07_verification_operations_plan.md` §4.1, `docs/README.md` D-42)*

### Q21. 대시보드에 표시되는 차단율과 실제 보안 탐지율(Detection Rate)은 왜 다른가요?
**A:** 대시보드의 차단율은 실제 인입된 총 요청 중 차단된 '운영 이벤트의 비율'일 뿐이며, 정상 질의가 대다수인 환경에서는 수치가 낮게 나옵니다. 반면 탐지율은 공격 라벨이 붙은 통제된 시험셋에서 공격을 몇 건 맞췄는지를 뜻하므로 두 지표의 정의를 엄격히 분리하여 왜곡을 방지했습니다.  
*(근거: `docs/04_screen_design.md` L294, `docs/07_verification_operations_plan.md` §1.2)*

### Q22. 제3자 독립 시험셋 측정을 진행하지 않은 이유는 무엇인가요?
**A:** 학계 벤치마크나 외부 레드팀 데이터셋을 적용하기 위한 사전 스크립트는 준비되었으나, 제한된 11주의 개발 기간 동안 엔드투엔드 파이프라인 완성도와 안정적 시연 인프라 구축에 우선순위를 두었기 때문입니다. 수치를 지어내지 않고 미측정 사실을 정직하게 명시하는 것이 공학적 윤리에 부합한다고 판단했습니다.  
*(근거: `docs/07_verification_operations_plan.md` §8.3, `docs/presentation/presentation.html` L109)*

## 5. 운영 및 유지보수

### Q23. 새로운 공격 패턴이 발견되었을 때 서버를 재시작하지 않고 규칙을 반영할 수 있나요?
**A:** 가능합니다. 보안 규칙은 불변 버전 관리되는 `threat_intel.rulesets` 테이블에 저장되며, 관리자가 관제 화면에서 게시(Publish)를 승인하면 백엔드가 10초 주기 폴링을 통해 메모리 내 룰 스냅샷을 무중단(Zero-downtime)으로 핫스왑합니다.  
*(근거: `docs/06_guardrail_security_design.md` §5.1, `backend/app/threat_intel/engine.py` L60)*

### Q24. AI가 추천한 정규식 규칙을 왜 즉시 차단에 투입하지 않고 '관찰(Observe) 모드'를 두나요?
**A:** AI가 생성한 정규식에 미처 예상치 못한 오탐 조건이 포함되어 있을 경우 정상 고객의 질의가 대량 차단되는 사고가 발생할 수 있기 때문입니다. '관찰 모드'에서는 차단하지 않고 로그만 남겨 모니터링한 뒤, 이상이 없을 때 정식 차단 모드로 승격시킵니다.  
*(근거: `docs/06_guardrail_security_design.md` §3.5, `docs/README.md` D-47)*

### Q25. 새로 배포한 룰셋에 심각한 오탐이 발생하면 어떻게 롤백하나요?
**A:** 관제 대시보드의 '규칙·정책' 메뉴에서 과거의 안정된 룰셋 버전 ID를 선택하고 관리자 암호를 입력하면 즉시 이전 스냅샷으로 롤백됩니다. 룰셋은 덮어쓰지 않고 버전별로 불변 레코드가 보관되므로 1초 내로 복구가 가능합니다.  
*(근거: `docs/06_guardrail_security_design.md` §5.2, `backend/app/api/ops.py` L330)*

### Q26. 실시간 관제 경보(Alert)는 어떤 조건에서 트리거되나요?
**A:** 관찰 모드 규칙에 단시간 내 반복 질의가 감지될 때, LLM 판별 서버의 타임아웃이 연속 발생할 때, 그리고 단일 IP에서 임계치를 초과하는 차단 이벤트가 집중될 때 비동기 감사 스케줄러가 경보 테이블(`audit.alerts`)에 즉시 이벤트를 생성합니다.  
*(근거: `docs/01_system_architecture.md` §5.2, `docs/README.md` D-47)*

### Q27. 침해 사고 감사 보고서(PDF)는 어떤 기술로 생성되며 한글 깨짐은 없나요?
**A:** ReportLab 4.2 라이브러리를 사용하여 생성되며, 리눅스 도커 컨테이너 내부의 나눔고딕(`NanumGothic.ttf`) 폰트를 PDF 바이너리 자체에 직접 임베딩(TTFont)하여 어떤 기기에서 열람해도 한글 깨짐 없이 동일하게 렌더링됩니다.  
*(근거: `backend/app/audit/report.py` L25, `docs/README.md` D-21)*

## 6. 1인 개발 및 엔지니어링 수행

### Q28. 1인이 감당하기에 백엔드, 프론트, 보안, DB까지 범위가 방대했을 텐데 11주 공정을 어떻게 완성했나요?
**A:** 개발 착수 전 시스템 설계 문서(DES-000~007)와 결정 기록(D-01~D-48)을 철저히 작성하여 아키텍처의 모호성을 완전히 제거하고 시작했기 때문입니다. 1주차 말에 백엔드 API 규격을 조기에 동결(PLN-006 ★)하여 불필요한 결합 마찰을 방지하고, 명확한 완료 기준(DoD)에 따라 모듈별로 집중 구현하여 24개 세부 작업을 11주 내에 무결점으로 완수했습니다.  
*(근거: WBS 2안 `AI_보안_가드레일_챗봇_WBS.html`, `Gantt_Chart.html`)*

### Q29. 1인 개발 과정에서 코드 품질과 보안성을 어떻게 객관적으로 검증했나요?
**A:** 주관적 판단을 배제하기 위해 pytest 기반의 격리 DB 통합 테스트 393건을 구축하여 배포 전 무결성을 검증했습니다. 또한 Playwright를 통해 실제 크로미움 브라우저에서 쇼핑몰, 관제 대시보드, LAB 비교 화면의 종단간(E2E) 시나리오를 자동 실행하여 UI와 API의 결합 안정성을 입증했습니다.  
*(근거: `scripts/e2e_ops.py`, `scripts/e2e_web.py`, `docs/07_verification_operations_plan.md` §2)*

### Q30. 개발 과정에서 가장 풀기 어려웠던 기술적 난관과 이를 해결한 경험은 무엇인가요?
**A:** CPU 추론 지연이었습니다. 질문 하나에 모델을 여러 번 불러 응답이 20~50초 걸리고, 판별이 시간 초과로 실패하기도 했습니다. 실측(생성 약 7 tokens/s)을 기준으로 호출 예산과 타임아웃을 다시 정하고(판별 45초), 쇼핑몰 화면에 처리 단계 칩을 실시간으로 보여 주었습니다(D-35). 또 정상 장바구니 요청이 모델의 ID 추측 때문에 차단되던 문제를 형식 오류는 되돌려 재시도하는 방식으로 고쳤습니다(D-44, D-45).  
*(근거: `docs/README.md` D-15, D-35, D-44, D-45)*

### Q31. 이 가드레일 시스템을 패션 쇼핑몰 외에 다른 도메인(금융, 의료 등)에도 재사용할 수 있나요?
**A:** 가능합니다. 가드레일 엔진 코드(`backend/app/guardrails/`)는 상거래 로직과 분리된 모듈이며, 도메인별 고유 정책은 데이터베이스의 룰셋 테이블(`threat_intel`)과 판별기 프롬프트 설정만 교체하면 즉시 타 도메인에 적용 가능한 범용 아키텍처를 지니고 있습니다.  
*(근거: `docs/01_system_architecture.md` §2.2, `docs/06_guardrail_security_design.md` §1.1)*

### Q32. 이번 프로젝트를 수행하면서 느낀 가장 큰 공학적 교훈은 무엇인가요?
**A:** "완벽한 단일 방패는 없으며, 투명한 감사 추적성과 최소 권한 원칙이 최고의 보안이다"라는 점입니다. LLM의 환각과 취약성을 억지로 100% 막으려 하기보다, 빠른 규칙과 유연한 AI를 결합하고, 인간 승인(HITL)으로 위험한 동작을 통제하며, 모든 증적을 투명하게 남기는 다계층 방어 체계의 가치를 체득했습니다.  
*(근거: `docs/README.md` D-05, D-25, D-36)*
