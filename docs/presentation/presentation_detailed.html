🛡️ 계층 간 데이터 전달 시의 핵심 보안 원칙

1. 단일 진입점 원칙
모든 트래픽은 Nginx를 통해서만 내부로 들어올 수 있으며, 클라이언트가 내부 컨테이너 IP나 포트에 직접 접근하는 경로는 물리적으로 차단됩니다.
2. 채널 위조 불가 원칙
외부에서 들어온 요청은 Nginx가 X-Edge-Channel: shop을 강제 주입하므로, 해커가 관리자 권한 API를 호출할 방법이 원천 차단됩니다.
3. 원자적 감사 커밋
FastAPI에서 처리된 질의 결과는 PostgreSQL의 audit.outbox에 비즈니스 데이터와 한 트랜잭션으로 커밋되어 증적 누락이 0건입니다.

3. [심층 해설] Nginx는 무엇을 하는 애인가?

💡 한 줄 정의: Nginx(엔진엑스)는 비신뢰 외부 인터넷망과 신뢰 내부 백엔드망 사이에 위치하여, 트래픽을 중계하고 암호화(SSL)를 해제하며 악성 요청을 1차로 걸러내는 초고속 보안 리버스 프록시(Reverse Proxy)이자 정적 웹 서버입니다.

🛡️ 본 시스템에서 Nginx가 수행하는 6대 핵심 역할

🔒 1. SSL/TLS 종단 (HTTPS Termination)
고객 브라우저와의 모든 통신을 최신 암호화 프로토콜(TLS 1.2/1.3)로 보호합니다. 무거운 암호화/복호화 연산을 Nginx가 전담하여 내부 FastAPI 서버의 CPU 부담을 없애줍니다. (운영 443 포트 / LAB 8443 포트)
🌐 2. 도메인(SNI) 기반 경로 분리 및 은닉
하나의 서버에서 shop.example.internal(쇼핑몰)과 ops.example.internal(보안 관제 센터)을 완벽히 분리합니다. 미등록 도메인이나 직접 IP 접근은 HTTP 444(응답 없이 강제 연결 종료)로 드롭합니다.
🛡️ 3. 보안 채널 위조 방지 (X-Edge-Channel 강제)
해커가 클라이언트에서 임의로 X-Edge-Channel: ops를 위조하여 보내더라도, Nginx가 이를 무조건 삭제하고 shop으로 강제 덮어씁니다. 쇼핑 도메인으로 들어온 관제 API 접근은 Nginx 단계에서 404 Not Found로 원천 차단됩니다.
⚡ 4. 순수 JavaScript 정적 웹 초고속 서비스
쇼핑몰 웹 페이지(HTML, CSS, JS)를 파이썬 백엔드를 거치지 않고 Nginx가 디스크에서 다이렉트로 서비스합니다. 파이썬 백엔드는 오직 보안 검사와 API 처리에만 100% 집중할 수 있습니다.
🚦 5. DoS 방어 레이트 리밋 (Rate Limiting)
공격자가 챗봇을 마비시키기 위해 요청을 폭주시키는 것을 막기 위해, IP당 초당 10회(Burst 20회) 슬라이딩 윈도우 제한을 걸어 초과 트래픽을 Nginx 선에서 차단(HTTP 429)합니다.
📡 6. 보안 헤더 주입 및 실시간 SSE 버퍼링 해제
XSS 방어를 위한 강력한 CSP(Content-Security-Policy)와 X-Frame-Options: DENY를 자동 주입합니다. 또한 가드레일 진행 단계를 사용자에게 실시간 전송하기 위해 proxy_buffering off를 적용합니다.

⚙️ 실제 Nginx 설정 발췌 (보안 아키텍처 핵심)

# 쇼핑몰 서버 블록: 외부 공개 진입점
server {
    listen 8443 ssl;
    server_name shop.example.internal;

    # 정적 쇼핑 웹 서비스 (FastAPI 부하 분산)
    location / { root /usr/share/nginx/html/shop; try_files $uri $uri/ /index.html; }

    # 백엔드 API 프록시: 보안 채널 강제 주입 & 관제 API 경로 원천 차단
    location /api/ {
        proxy_pass http://backend:8000;
        proxy_set_header X-Edge-Channel "shop";   # 클라이언트 위조 무력화!
        proxy_set_header X-Real-IP $remote_addr;
        proxy_buffering off;                     # 가드레일 실시간 단계 표시용 SSE
    }
    location ~ ^/api/v1/(audit|rulesets|alerts|lab) { return 404; } # 관제 API 접근 차단
}

4. [심층 해설] PostgreSQL 17은 어떤 역할을 하는가?

💡 한 줄 정의: PostgreSQL 17은 본 프로젝트의 중앙 저장소로서, 단순 데이터 저장을 넘어 3개 스키마 분리(비즈니스·보안룰·감사), 트랜잭셔널 아웃박스(Outbox) 패턴, 그리고 7단계 최소 권한 역할(RBAC)을 통해 데이터 무결성과 보안을 강제하는 엔터프라이즈 RDBMS입니다.

🗄️ 1. 3개 논리 스키마(Schema)의 분리와 역할

스키마 이름 보관 데이터 보안 및 아키텍처적 의의
commerce
(이커머스 비즈니스)		 고객 계정(Argon2id 해시), 세션, 장바구니, 주문 내역, 쿠폰, 변경 제안(actions) 고객의 일상적인 쇼핑 데이터. AI가 직접 수정할 수 없으며, 모든 변경은 actions 테이블에 제안 상태로 등록된 후 고객 승인을 거침.
threat_intel
(위협 지능 & 룰)		 가드레일 정규식 룰 49종, 룰셋 버전, 활성화 정책, 게시/롤백 감사 이력 FastAPI 메모리 캐시로 동기화되는 룰 저장소. 운영 중에도 서버 재부팅 없이 신규 룰을 즉시 배포(Hot-Reload)하는 원천 데이터.
audit
(보안 감사 로그)		 보안 이벤트(events), 룰 적중(rule_hits), 도구 실행(tool_executions), outbox 대기열 사후 침해 분석을 위한 포렌식 증적 저장소. 고객 원문은 일체 저장하지 않고 마스킹된 요약과 해시 지문만 기록(개인정보보호법 준수).

🔄 2. 트랜잭셔널 아웃박스 패턴 (Transactional Outbox Pattern)

일반적인 시스템에서는 챗봇 응답과 감사 로그 저장을 따로 처리하다가 네트워크 장애 시 감사 로그가 유실되는 문제가 발생합니다.

본 프로젝트의 해결책:
FastAPI는 비즈니스 처리와 감사 데이터를 audit.outbox 테이블에 하나의 DB 트랜잭션(Atomic)으로 묶어 커밋합니다. 만약 감사 저장이 실패하면 답변 전송 자체가 거부(Fail-Closed)됩니다. 이후 별도의 백그라운드 프로세스인 audit-worker가 FOR UPDATE SKIP LOCKED를 사용해 무손실로 감사 테이블에 적재합니다.
🛡️ 3. 7대 최소 권한 DB 역할 (RBAC)
단일 관리자 계정(root)을 쓰지 않고 역할을 7개로 쪼개어 침해 확산을 방지합니다:
  • auth_service: 계정 로그인 및 토큰 갱신 전용
  • shop_reader / shop_writer: 상품 조회 및 장바구니 수정 전용
  • rule_reader / rule_publisher: 룰셋 조회 및 관리자 게시 전용
  • audit_ingest: 오직 outbox에 감사 봉투 INSERT만 가능
  • audit_worker: outbox 읽기 및 events 테이블 적재 전용
👉 쇼핑 API가 해킹당하더라도 감사 로그를 삭제하거나 룰을 변조할 수 없습니다!

5. [심층 해설] FastAPI, Ollama, Streamlit, AnythingLLM

⚡ FastAPI (가드레일 백엔드 게이트웨이)

왜 FastAPI인가? 파이썬 최신 비동기(Async/Await) 프레임워크로, 고성능 ASGI 기반의 동시성 처리와 엄격한 Pydantic 스키마 검증을 제공하기 때문입니다.

  • 파이프라인 오케스트레이션: 입력 검사 → 모델 추론 → 도구 검증 → 출력 검사의 전 과정을 비동기로 지연 없이 조율합니다.
  • 실시간 단계 스트리밍: 답변 생성 전이라도 ① 질문 검사 → ② 답변 생성 → ③ 답변 검사 진행 상태를 브라우저로 SSE 전송합니다.
  • Fail-Closed 강제: 가드레일 모듈이나 감사 로깅 중 하나라도 에러가 나면 통과시키지 않고 즉시 503 오류로 안전하게 방어합니다.
🧠 Ollama & qwen3:8b (로컬 SLM 인프라)

왜 외부 OpenAI 대신 로컬 SLM인가? 고객의 장바구니, 비밀번호, 사내 영업 기밀이 외부 클라우드로 유출되는 것을 100% 원천 방지하기 위함입니다.

  • 데이터 주권(Data Sovereignty): 온프레미스(LAN 10.10.70.65)에서 실행되어 외부 인터넷과 완전 격리된 에어갭 환경을 유지합니다.
  • CPU 추론 엔지니어링: 실측 초당 7.2토큰의 CPU 한계를 고려하여 최대 토큰 512개, 문맥 8,192개, 45초 타임아웃 예산을 엄격히 통제합니다.
  • 경계 토큰 격리 (Boundary Delimiter): 판별 대상 문장을 BOUNDARY-<hex> 무작위 토큰으로 감싸 모델이 프롬프트를 지시문으로 오인하지 않도록 방어합니다.
📊 Streamlit (보안 관제 센터 Web UI)

왜 Streamlit인가? 데이터 시각화와 상호작용 UI를 파이썬 코드로 신속히 구축하여, 보안관(SecOps)이 직관적으로 상황을 통제할 수 있습니다.

  • 실시간 대시보드: 실시간 차단 건수, OWASP Top 10 분류별 통계, 상세 감사 로그 및 매칭된 정규식 규칙 ID를 시각화합니다.
  • 무중단 룰 배포 (Zero-Downtime Hot-Reload): 신종 제로데이 공격 발생 시 웹에서 룰을 수정하고 검증 후 1초 만에 서버에 즉시 적용합니다.
  • LAB A/B 비교 모드: 동일한 공격 프롬프트를 가드레일 ON/OFF 환경에서 나란히 실행하여 방어 효과를 실시간 비교 시연합니다.
🤖 AnythingLLM 연동 (외부 챗봇 보안 통제)

외부 프로그램 연결 시의 위협과 방어: 기업에서 널리 쓰이는 데스크톱 챗봇(AnythingLLM)을 사내 쇼핑몰 API에 연결할 때의 보안을 검증합니다.

  • OpenAI 호환 API 제공: 표준 /v1/chat/completions 규격을 지원하여 다양한 사내 클라이언트와 원활히 연동됩니다.
  • 지시문 강등 정책 (Prompt Demotion): 외부 앱이 임의로 주입하는 시스템 프롬프트는 관리자 권한이 아닌 '비신뢰 참고자료'로 강등하여 검사합니다.
  • 원격 변경 차단: AnythingLLM 화면에서는 데이터 변경 승인을 할 수 없으며, 반드시 쇼핑몰 웹 확인 창으로 유도합니다.

7.1 시스템 안정성을 보장하는 5대 엔지니어링 처리 규칙

⚙️ 5대 엔지니어링 처리 규칙 상세 분석

핵심 규칙 상세 구현 원리 및 보안 효과
1. 검사 후 전송
(All Checks First)		 AI의 토큰을 클라이언트에 실시간으로 흘려보내지(Raw Streaming) 않습니다. 출력이 완전히 생성되고 3단계 가드레일 검사가 100% 끝난 후에만 최종 검증된 답변을 전송합니다. 사용자 대기 경험을 위해 대기 중에는 SSE로 '진행 단계 이름'만 전송합니다.
2. OR 판정 로직
(Rule OR AI)		 정규식 규칙과 AI 판별기 중 단 하나라도 공격으로 판단하면 무조건 차단합니다. 공격자가 복잡한 우회 문장을 쓰든, 기계적인 키워드를 쓰든 빈틈없이 방어합니다.
3. 두 계층 동시 실행 및 기록 정규식 규칙이 먼저 공격을 잡더라도, 관제 분석을 위해 AI 판별기도 백그라운드로 실행하여 "규칙만 잡았는지, 둘 다 잡았는지" 증적을 감사 테이블에 정확히 남깁니다. (신종 위협 조기 식별)
4. 실패 시 거절
(Fail-Closed)		 AI 모델 서버 장애, 검사 시간 초과(45초), 룰 캐시 오류 발생 시 절대 "통과"시키지 않고 즉시 "잠시 후 다시 시도해주세요(HTTP 503)"로 거절하여 잠재적 취약점을 차단합니다.
5. 감사 기록 우선 원칙 감사 봉투가 DB audit.outbox에 완전히 커밋되지 않으면 클라이언트에게 답변을 전송하지 않습니다. 시스템 장애가 발생해도 감사 증적 누락이 원천적으로 불가능합니다.

🛡️ 제로 트러스트 실현
모든 입력과 출력에 대해 단 0.1%의 예외도 허용하지 않으며, 시스템 에러 시 가장 보수적인 안전 상태(503 거절)로 수렴합니다.
⚡ 사용자 체감 성능 개선
검사 후 전송으로 인한 대기 시간(약 20~30초) 동안 실시간 SSE 상태 알림을 제공하여 화면 멈춤 현상(Frozen UI)을 완벽히 방지합니다.

🛡️ 네트워크 보안의 3대 핵심 원칙

1. 포트 미공개 원칙 (Zero Public Ports)
외부 호스트에 바인딩되는 포트는 오직 Nginx(443/8443) 단 하나뿐입니다. FastAPI(8000), Streamlit(8501), PostgreSQL(5432) 포트는 호스트에 일체 노출되지 않고 Docker 내부망에서만 통신합니다.
2. 티어 간 네트워크 격리 (Bridge Isolation)
웹 클라이언트가 통신하는 edge 네트워크와 데이터베이스가 위치한 app 네트워크를 분리하여, 웹 서버가 탈취되더라도 DB로의 직접 접근을 차단합니다. 모델 서버는 model 네트워크로만 연결됩니다.
3. 운영 환경과 LAB 실습 환경의 물리적 분리
운영 환경(443)은 가드레일을 끌 수 없는 엄격한 보안 모드로 작동하며, 실습용 LAB 환경(8443)은 독립된 DB와 합성 데이터를 사용하여 가드레일 ON/OFF A/B 실시간 공격 시연을 안전하게 수행합니다.

10. 어떤 기준으로 개발했는가? 7대 설계 원칙 & 결정 기록

📐 7대 핵심 엔지니어링 설계 원칙

원칙 구체적 의미와 시스템 구현 내용
1. 모델은 권한 판정자가 아니다 AI 모델 자체에는 DB 쓰기나 셸 권한이 일체 없습니다. 서버 코드가 정해진 고정 SQL로 본인 데이터만 조회하며, 모든 변경은 사람이 직접 승인합니다. (D-05, D-13)
2. 가드레일은 서버가 강제한다 운영 환경에서는 어떤 클라이언트 요청으로도 가드레일을 끌 수 없습니다. ON/OFF 비교는 격리된 LAB 환경에서만 가능합니다. (D-03, D-21)
3. 실패하면 막는다 (Fail-Closed) 판별 실패, 검사 시간 초과, 감사 로그 저장 실패 등 예외 상황 발생 시 요청을 통과시키지 않고 즉각 거절합니다. (D-08, D-25)
4. 검사 후 전송 원칙 모델이 생성하는 토큰을 즉시 반환하지 않고, 전체 응답에 대한 가드레일 검사가 100% 완료된 후에만 클라이언트에 전송합니다. (D-04)
5. 최소 권한 분리 (Least Privilege) DB 로그인 역할을 7개로 쪼개고, 쇼핑 도메인에서는 관리자 관제 API를 물리적으로 차단합니다. (D-17)
6. 원문을 남기지 않는다 (Data Minimization) 운영 감사 DB에는 마스킹된 요약과 룰 ID만 저장하고 대화 원문은 저장하지 않아 개인정보 침해를 원천 방지합니다. (D-09)
7. 정직한 측정과 검증 목표값과 실제 측정치를 엄격히 구분하며, 룰 개발에 사용한 시험셋으로 탐지율을 과장하지 않습니다. (D-07)

16. 부록: 심사위원/교수님 기술 방어 질의응답 (Q&A)

Q1. Nginx를 굳이 FastAPI 앞에 둔 진짜 기술적 이유는 무엇인가요? 직접 노출하면 안 되나요?
답변: 파이썬 기반 Uvicorn/FastAPI를 직접 외부에 노출하는 것은 엔터프라이즈 보안상 매우 위험합니다. Nginx를 배치함으로써 (1) 무거운 TLS 암호화 연산을 전담하여 백엔드 CPU를 보호하고, (2) 고객 쇼핑몰(shop)과 보안 관제(ops) 도메인을 SNI 레벨에서 완벽히 격리하며, (3) 해커가 X-Edge-Channel 헤더를 위조하여 관리자 API를 호출하는 공격을 Nginx 선에서 강제로 덮어써서 원천 무력화합니다. 또한 비정상 트래픽에 대한 DoS Rate Limiting을 백엔드 도달 전에 1차 차단합니다.
Q2. PostgreSQL에서 단일 DB를 쓰면서 보안 격리가 충분하다고 볼 수 있나요?
답변: 물리적으로는 1대의 PostgreSQL 17이지만, 논리적으로 commerce, threat_intel, audit 3개의 스키마로 분리하고 7개의 세분화된 DB 역할(Role)을 적용했습니다. 쇼핑몰 웹 API에 쓰이는 계정(shop_writer)은 감사 스키마나 룰 스키마에 대한 쓰기/삭제 권한이 전무합니다. 따라서 웹 서비스에 SQL Injection 취약점이 발생하더라도 감사 로그를 삭제하거나 보안 룰셋을 변조하는 횡적 이동(Lateral Movement)이 원천 불가능합니다.
Q3. 트랜잭셔널 아웃박스(Transactional Outbox) 패턴을 왜 도입했나요?
답변: 챗봇 답변을 클라이언트에 전달하는 트랜잭션과 보안 감사 로그를 기록하는 작업이 분리되어 있으면, 네트워크 순단이나 서버 다운 시 "답변은 나갔는데 누가 무슨 공격을 했는지 로그가 유실되는 문제"가 생깁니다. 이를 방지하기 위해 audit.outbox 테이블에 단일 트랜잭션으로 원자적(Atomic) 기록을 보장하고, 백그라운드 워커가 SKIP LOCKED로 무손실 비동기 이관하도록 설계했습니다.
Q4. AI 판별기 자체가 프롬프트 인젝션에 당해 탈옥될 위험은 없나요?
답변: 철저한 샌드박스 격리 설계를 적용했습니다. 판별할 사용자 문장은 요청마다 난수로 생성되는 BOUNDARY-<hex> 경계 태그로 완벽히 감싸 "명령문이 아닌 데이터"로만 모델에 주입됩니다. 또한 모델의 답변 형식도 다른 문장 없이 오직 {"label": "SAFE" | "ATTACK"} 단일 JSON 스키마만 허용하므로, 모델이 탈옥되어 부가적인 악성 명령을 출력하더라도 파서 단계에서 즉각 무효 처리되어 거절됩니다.
